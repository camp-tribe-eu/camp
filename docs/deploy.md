# Викочування застосунку на сервер

CAMP-61. Написано 15.10.2026. Кожне число тут має команду, якою його
отримано; число «живого» стану (скільки міграцій чекає, який реліз
чинний) дивись командою, а не в цьому файлі: воно рухається.

**Що зараз на проді — одна команда:**

```bash
export CAMPTRIBE_HOST=root@<адреса>      # адреси в репозиторії немає навмисно
./infra/deploy-app.sh --status
```

Вона читає, не міняє нічого, і відповідає на п'ять питань разом:
який реліз чинний і з якого він коміту; чи справді з цієї теки працюють
процеси API й веб (а не лише чи «служба active»); чи віддає веб статику
саме цієї збірки; чи збігається схема БД із тим, що знає код; чи збігається
це з історією перемикань. Код виходу `0` — усе збігається, `1` — є
розбіжність, названа поіменно.

## 0. Як це влаштовано

```
ноутбук                                      сервер (/srv/camptribe)
infra/deploy-app.sh  ──ssh──►  bash <тимчасовий файл>  =  infra/bin/camptribe-deploy
 (розв'язує SHA,                releases/<7 hex>/        ← кожен реліз окремо, зі своїм
  дістає міграції з git)                  RELEASE.json   ← повний SHA, хто, коли, BUILD_ID
                                current → releases/…     ← перемикається атомарно
                                deploy-history.jsonl     ← що перемикали, ким, чи вдалось
                                deploy.log, backups/predeploy-*.dump
```

* Збірка йде **на сервері**: вона читає API на льоту й робить із нього
  65 тис. сторінок, тож їй потрібна БД. Реліз = 8.6 ГБ, з них `.next`
  7 839 МіБ; збірка ≈ 400 с (заміряно 12.10.2026 на CPX32).
* `deploy-app.sh` кладе на машину **рівно той файл виконавця, що лежить
  поруч у твоєму checkout**, а не встановлений колись у `/usr/local/bin`.
  Тому «що запускається» = «що ти переглянув у коміті». Встановлена копія
  (її кладе `deploy-infra.sh`) існує для аварії, коли ноутбука немає.
  🔴 **Доки не виконано `./infra/deploy-infra.sh --apply`, на машині лежить
  СТАРА версія, яка перемикає й перезапускає без `--apply`.** Через
  `deploy-app.sh` це не страшно (він її не викликає), через ssh-руками на
  машині — страшно. Станом на 15.10.2026 вона побайтно збігається з версією
  до CAMP-61 (`diff`: IDENTICAL).
* Файл виконавця ліпиться на `/run`, а `/run` на сервері змонтовано `noexec`
  (заміряно: `Permission denied`, код 126), тому запуск іде як `bash <файл>`.
* Деплоїться **SHA, а не гілка**: за ті хвилини, що йде збірка, `main`
  може піти вперед, і «викотили main» означало б не те, що ти перевірив.

## 1. Один раз: робоче місце

1. Ключ SSH на машину: `~/.ssh/id_ed25519_camptribe_server` (або
   `CAMPTRIBE_KEY=…`). Без ключа далі нічого не працює.
2. `export CAMPTRIBE_HOST=root@<адреса>`. Адреса **не** лежить у репозиторії:
   він публічний.
3. Перевір, що бачиш прод: `./infra/deploy-app.sh --status`. Очікуєш
   `ВИСНОВОК: усе збігається`. Якщо ні, спершу розберись із цим, а не
   викочуй поверх.

## 2. Викотити

0. **PR злито, CI зелений.** Деплоїться те, що на `origin`; локальний
   коміт, якого там немає, обгортка відхилить до будь-якого `ssh`.
1. **Сухий прогін** (за замовчуванням він і є):

   ```bash
   ./infra/deploy-app.sh                 # origin/main
   ./infra/deploy-app.sh --sha <sha>     # або конкретний коміт
   ```

   Він нічого не змінює і друкує: повний SHA й тему коміту, який реліз
   чинний, скільки місця на диску, **які міграції чекають**, що буде
   прибрано після успіху, і порядок кроків. Прочитай це.
2. **Є міграції?** Прочитай їхні файли `apps/api/src/migrations/` і
   перевір правило з розділу 5: лише додають. Якщо хоч одна щось видаляє,
   перейменовує чи робить `NOT NULL` без значення за замовчуванням, **стоп**:
   її мусить розбити на два релізи автор, не ти.
3. **Викотити:**

   ```bash
   ./infra/deploy-app.sh --apply                 # без міграцій
   ./infra/deploy-app.sh --apply --migrate       # якщо сухий прогін показав чекаючі
   ```

   Без `--migrate` при чекаючих міграціях скрипт відмовляє **до збірки**
   (код, що чекає колонок, не можна класти на схему без них).
4. **Що відбувається** (і скільки): fetch за SHA → [знімок БД → міграції]
   → `npm ci` + збірка API → тимчасова нова API на порту 3002 → збірка вебу
   **проти неї** (≈400 с) → `RELEASE.json` → `current` перемикається,
   служби перезапускаються → перевірка → прибирання старих релізів.
   Довгий крок один, збірка. Розрив ssh його не зупиняє (скрипт ігнорує
   SIGHUP), а лог лежить у `/srv/camptribe/deploy.log`. Перед вироком
   скрипт чекає, поки служби відповідять, **до 60 с** (30 спроб по 2 с):
   якщо нова API піднялась не там чи не піднялась, провал виявляється
   за ≈60 с, плюс ≈2 с на повернення. Заміряно 15.10.2026 у репетиції з
   навмисно зламаним `PORT`: **64 с** від початку `switch` до «повернуто й
   перевірено», код 3.
5. **Прочитай код виходу:**

   | код | що це | що робити |
   | --- | --- | --- |
   | `0` | реліз віддається, перевірку пройдено | перейти до п. 6 |
   | `1` | відмова **до** будь-якої зміни (передумова, `--migrate`, диск, колізія) | прочитати причину, виправити, повторити |
   | `3` | викотили, перевірка не пройшла, **попередній реліз повернуто й перевірено** | прод цілий; розбирати причину за виводом; БД лишається мігрованою (розділ 5) |
   | `4` | викотили, не пройшло, **і повернути перевіреним не вийшло** | 🔴 стан невідомий: `--status`, потім `--rollback --to <реліз> --apply` вручну |
6. **Подивись очима:** `./infra/deploy-app.sh --status` має дати
   `усе збігається` з **новим** комітом, а сайт відкритись у браузері без
   помилок у консолі. «Служба active» нічого не доводить: вона буває
   active на старому каталозі.

## 3. Відкотити

```bash
./infra/deploy-app.sh --rollback              # сухий прогін: куди й чому
./infra/deploy-app.sh --rollback --apply      # відкотити
./infra/deploy-app.sh --rollback --to <реліз> --apply   # явна ціль
```

* **Відкат = «скасувати останнє перемикання»**, за `deploy-history.jsonl`.
  Другий `--rollback` скасовує перший, тобто вертає вперед. Раніше ціль
  вибирала «найновіша тека не чинна за mtime», і mtime міняється від чого
  завгодно.
* Якщо історії немає (перший керований деплой ще не було) або `current`
  вказує не туди, куди каже історія, скрипт **не вгадує**, а просить
  `--to` і перелічує наявні релізи.
* Це **та сама процедура**, що й деплой: перемкнути, перезапустити,
  перевірити процеси й статику, повернути, якщо не пройшло. Окремого
  «аварійного» коду немає, бо код, яким не користуються, не працює.
* **Чого відкат не повертає: БД.** Схема лишається такою, якою стала.
  Старий код працює на новій схемі лише якщо міграції були адитивні
  (розділ 5), і скрипт каже про це перед відкатом: `схема БД ПОПЕРЕДУ
  релізу … на N міграцій`.
* **`.env` відкочується разом із релізом:** кожен реліз має власну копію
  (`apps/api/.env`, береться з чинного при збірці). Якщо `.env` чинного
  змінювали після деплою, відкат поверне значення старого релізу; скрипт
  попереджає, коли хеші розійшлись.
* Скільки це триває: див. розділ 4, число з репетиції.

## 4. Репетиція відкату

Відкат, яким не користувались, не існує. Репетиція ганяє **ті самі**
команди `switch` і `rollback --apply`, що й бойовий деплой, але над
іншим коренем, іншим симлінком, іншими юнітами на портах 3100/3101.
Бойові `current`, `camptribe-api` і `camptribe-web` не чіпаються.

```bash
./infra/deploy-app.sh --rehearse              # сухий прогін: що створить
./infra/deploy-app.sh --rehearse --apply      # відрепетирувати і все прибрати
```

Що вона створює: `/srv/camptribe-rehearsal` з двома релізами (жорсткі
посилання на справжні збудовані, місця майже не займають) і два юніти
`camptribe-rehearsal-{api,web}` у `/run/systemd/system` (зникають навіть
при перезавантаженні). Юніти працюють із `ProtectSystem=strict` і
порожнім `ReadWritePaths`: файли під ними ті самі inode, що в проді, тож
записати в бойовий файл вони не мають змоги, і це **перевіряється пробою
запису перед стартом**. Наприкінці скрипт доводить, що бойове не рушило
(`current`, MainPID і час старту служб ті самі), і що лічильник посилань
бойових файлів знову 1.

**Результат репетиції 15.10.2026, 08:16 UTC, на справжньому сервері**
(`./infra/deploy-app.sh --rehearse --apply`, код 0):

| що | число |
| --- | --- |
| `switch 73d1710 → fd3b06b` разом із перевіркою | **2 с** |
| `rollback fd3b06b → 73d1710` разом із перевіркою | **2 с** (3 с вся команда з передумовами: `date +%s` до й після) |
| що повернулось | процеси API й веб (pid 96799/96824 → 97337/97362) знову працюють із теки `73d1710`; статика збірки `HwgXdu8wS1PeR5iA7UuVD` → `T8MiXPAzAPkVgR1dTUajr` → `HwgXdu8wS1PeR5iA7UuVD`; після відкату стара збірка відповідає 200, нова 404 |
| бойове до й після | `current → fd3b06b`, MainPID і час старту api/web ті самі; у `/srv/camptribe` за вікно репетиції змінено **0 файлів** (`find -newermt`, `node_modules` включно); відбиток дерева ідентичний, крім mtime самого `/srv` |
| залишки | 0: ні `/srv/camptribe-rehearsal`, ні юнітів, ні портів 3100/3101, ні файлів із лічильником посилань > 1 |

У журналі репетиційного веба буде `Failed to update prerender cache …
EROFS: read-only file system`: це **не помилка**, а пісочниця, що не
пускає запис у файли, спільні з продом; сторінки вона віддає як належить.

🔴 **Чого репетиція не покриває:** обидва релізи тут збудовані до CAMP-61 і
не мають `RELEASE.json`, тож гілку з маніфестом перевірено лише
самотестом, а не на сервері. Перша справжня викладка її перевірить.

Повторюй репетицію перед кожною віхою (запуск, зняття пароля) і після
будь-якої зміни `infra/bin/camptribe-deploy`.

## 5. Міграції

**Коли: до перемикання, з коду нового релізу.** Порядок у деплої такий:

```
збірка API нового релізу ─► знімок БД ─► migration:run ─► тимчасова нова API
  ─► збірка вебу проти неї ─► перемикання ─► перевірка
```

Чому саме так, а не після перемикання: веб збирається з API на льоту, а нова
API читає колонки, яких у старій схемі немає. Заміряно 15.10.2026: між живим
`fd3b06b` і `main` 46 файлів `apps/api/src`, зокрема сутність
`camping-spot` із колонками `warning_areas` і `overnight_*`; їх створюють
міграції `WarningAreas` і `SpotOvernight`. Нова API на непромігрованій
схемі падає на кожному запиті до `camping_spots`; веб, зібраний проти
**старої** API, не впав би, а мовчки не мав би цих даних.

**Що мусить виконуватись, щоб це було безпечно, і це правило авторам
міграцій, а не скрипту:** міграція має бути **адитивною**: старий код
(який ще обслуговує сайт під час збірки, а після невдачі повернеться)
мусить працювати на новій схемі.

| можна в одному релізі | лише у наступному, коли попередній уже не потрібен для відкату |
| --- | --- |
| `CREATE TABLE`, `CREATE INDEX` | `DROP COLUMN`, `DROP TABLE` |
| `ADD COLUMN` nullable або `NOT NULL DEFAULT <константа>` | `RENAME COLUMN` / `RENAME TABLE` |
| додати `CHECK`, який старий код не порушує | змінити тип колонки, `SET NOT NULL` без значення за замовчуванням |

🔴 Скрипт цього **не перевіряє**. Пошук «небезпечних слів» у міграції
не є властивістю (її обходить будь-яке нове слово), тож єдина перевірка
тут — рецензія PR. Скрипт гарантує інше: що міграції **не запускаються без
`--migrate`**, що перед ними зроблено й прочитано знімок, і що після них
звірено, що нічого не лишилось неприйнятим.

**Що відбувається, коли щось іде не так:**

| ситуація | що буде | перевірено |
| --- | --- | --- |
| міграція впала | `migration:run` іде в **одній транзакції** (`"all"`, за замовчуванням: `typeorm/commands/MigrationRunCommand.js:50`; `data-source.ts` цього не перекриває; `CONCURRENTLY` у міграціях немає), тож БД лишається як була; скрипт зупиняється, `current` не рушив, веб не збирався | самотест, випадок «міграція впала» |
| міграція пройшла, **перемикання впало** | код повертається на попередній реліз і це перевіряється; **БД лишається мігрованою**; `migration:revert` не викликається | самотест, випадок «міграція пройшла, перемикання впало» |
| знімок не вдався або не читається | міграцію не запущено | самотест (обидва випадки; повний `pg_dump` що вмирає посередині теж) |

Чому не робити `migration:revert` автоматично: `down()` адитивної
міграції видаляє колонку **разом із даними, записаними після неї**. Старий
код на новій адитивній схемі працює; видалення колонки назад — ні.

**Знімок:** `pg_dump -Fc` усієї БД у `/srv/camptribe/backups/predeploy-<реліз>-<час>.dump`,
тримаються три останні. Вага **163 047 252 байти (155 МіБ)**, **13,8 с** при
`nice -n 19` (заміряно 15.10.2026 на проді в `wc -c`, без запису на диск).
Це відновлення «на крайній випадок»: воно втрачає все записане після
знімка, тож робиться вручну й за рішенням власника. **Відновлення зі знімка
не відрепетирувано.**

## 6. Дані, що їдуть не з кодом: межі країн (CAMP-296)

`scripts/osm-pipeline/load-country-boundaries.sh` будує `osm_country_area`
з 27 екстрактів OSM. На сервері їх нема. Заміряно 15.10.2026:

| що | число | команда |
| --- | --- | --- |
| 27 екстрактів `*.osm.pbf` | **25 137 МБ (23,41 ГіБ)** | `stat -f %z *.osm.pbf` по сумі |
| уся робоча тека `~/camptribe-osm` | 31,0 ГіБ (це і є «31 ГБ» з картки: похідні файли поруч) | `du -sk` |
| таблиця `osm_country_area` | **41,0 МіБ** (40 МБ + 1,2 МБ індексів), 23 802 рядки, 2 379 137 вершин | `pg_table_size`, `pg_indexes_size` |
| `pg_dump -Fc -t osm_country_area` | **33 987 368 Б = 32,4 МіБ (34,0 МБ)**, 2,3 с | `pg_dump -Fc -t` |
| вільно на сервері | 115 ГБ | `df -h /srv` |

**Варіанти і ціна кожного:**

1. **Побудувати на ноутбуці, перенести лише таблицю.** *Рекомендовано.*
   Збірка на ноутбуці: **341 с**, пік пам'яті 1,66 ГБ (`/usr/bin/time -l`).
   Перенесення **34,0 МБ**: при заміряних **2,07 МБ/с** з ноутбука на сервер
   (100 МіБ за 50,55 с) це **≈16 с**. Відновлення на чисту базу: 0,51 с.
   Межа: потрібні 25 ГБ екстрактів **на ноутбуці**, тобто та сама тека, з якої
   зараз запускається `load-context.sh`, і та сама дата екстрактів.
2. **Качати екстракти на сервер і будувати там.** 25 137 МБ при заміряних
   **40,5 МБ/с** (100 МіБ за 2,59 с з сервера до Geofabrik) — **≈10 хв**
   завантаження, не 3,4 год, як з ноутбука (2,07 МБ/с). Але: **23,4 ГіБ диска
   на постійно** (20% вільного), на сервері **немає `osmium` і `ogr2ogr`**
   (`apt install osmium-tool gdal-bin`: системна зміна), збірка навантажує 4 vCPU
   живої машини (на ноутбуці 1 133 с процесорного часу), і її пишуть
   у **живу** БД (проміжні таблиці й обмін у транзакції).
   Час самої збірки на сервері не міряно: оцінка 8–15 хв.
3. **Збирати в CI й віддавати 34 МБ артефактом.** `osm-weekly.yml` уже тягне
   екстракти на раннер, ставить `osmium-tool gdal-bin` і публікує «data
   release». Додати до нього збірку таблиці й актив ≈34 МБ. Ціна: крок у
   воркфлоу; сервер бере актив із GitHub (потрібне рішення, чи публікувати
   похідну БД з OSM публічно: ODbL, питання для `camptribe-legal`, не для
   цього файлу). Розмір активу не міряно окремо: ті самі 2,4 млн вершин.

**Процедура за варіантом 1** (відрепетирувано локально, на сервері **ні**):

```bash
# на ноутбуці, з теки з екстрактами
DATABASE_URL=postgres://localhost:5432/<скретч-БД> ./scripts/osm-pipeline/load-country-boundaries.sh
pg_dump -Fc -t osm_country_area --no-owner --no-privileges <скретч-БД> -f osm_country_area.dump
shasum -a 256 osm_country_area.dump                    # запиши
scp osm_country_area.dump root@<адреса>:/root/          # ≈16 с

# на сервері, ПІСЛЯ деплою (у current мають бути скрипти CAMP-296). .env не виконуємо (`. .env`
# виконав би все, що там лежить), лише читаємо рядок; значення не друкуємо.
cd /srv/camptribe/current
export DATABASE_URL="$(grep '^DATABASE_URL=' apps/api/.env | cut -d= -f2-)"
[ -n "$DATABASE_URL" ] || echo "ПОРОЖНЬО — стоп"
shasum -a 256 /root/osm_country_area.dump                        # має збігтися із записаним
# єдина транзакція: при помилці стара таблиця (чи її відсутність) лишається
pg_restore --no-owner -d "$DATABASE_URL" -1 --exit-on-error --clean --if-exists /root/osm_country_area.dump
./scripts/osm-pipeline/load-country-boundaries.sh --tag-only     # секунди, екстрактів не читає
```

`--tag-only` на сервері потребує лише `psql` і `python3` (для `pg_conninfo`):
обидва там є (`command -v`, 15.10.2026); `osmium` і `ogr2ogr` не потрібні.
Він міняє `osm_ctx_place` і `osm_ctx_poi` (`ADD COLUMN country`, `UPDATE`
≈506 тис. рядків: 21 с локально), тож запускай поза піком.

Відрепетировано локально 15.10.2026: відновлення на чисту базу — рядки,
вершини й підпис по `iso` збігаються з оригіналом; обрізаний дамп
(20 МБ із 34) при `--clean -1` **не пошкодив існуючу таблицю** (до і після:
23802 рядки, 2 379 137 вершин). Версії збігаються: PostgreSQL 17.11 і
PostGIS 3.6.4 і локально, і на сервері.

🔴 `--tag-only` **не** запускає перевірку «живі кемпінги далі 2 км від
полігона» (вона є лише у повному шляху скрипта). Після відновлення на сервері
запусти її вручну: це запит із кінця `load-country-boundaries.sh`; поки його
не винесено окремо, скопіюй із скрипта. Це в `docs/after-launch.md`.

**Коди, які віддало джерело (31, а не 27):** 27 членів ЄС (`gr`, а не `el`;
`fi`, без `ax`) плюс `gi`, `mc`, `sm`, `va`. Це анклави в екстрактах сусідів;
фільтр ЄС-27 їх відсікає під час читання, не під час збірки.

**Хто запускає перерахунок** (`refresh-context-near.ts --apply --with-drift`,
24 013 кемпінгів): **власник**, після такого ланцюга: деплой (з міграціями) →
межі → `--tag-only` → `refresh-context-near.ts` **без** `--apply` → перегляд →
`--apply`. Репетиція «на копії» потребує копії БД; її в цій картці не
зроблено.

## 7. Чого процедура не вміє й не обіцяє

* **Атомарність `current`:** вона за побудовою (`rename(2)` через `mv -T`),
  а не за тестом. Тест на «лінк ніколи не зникає» був би флейкі.
* **Розрив ssh посеред збірки:** SIGHUP ігнорується (`trap '' HUP`), але
  цього не перевірено розривом справжнього з'єднання.
* **Відновлення БД зі знімка:** не автоматичне й не відрепетирувано.
* **Збірка на проді навантажує прод:** 400 с, до 5,1 ГБ купи Node при
  7,7 ГБ RAM, і веб-збірка б'є по тимчасовій API, не по живій; живу
  навантажує лише спільна БД. Сьогодні сайт закритий паролем; після
  відкриття це стає питанням.
* **Тимчасова API на час збірки** (порт 3002) на `main` піднімає
  `WarningsService`, який при старті й раз на 5 хв тягне 27 фідів MeteoAlarm
  у пам'ять (у БД не пише). На час збірки це подвоює опитування; якщо
  ліцензія MeteoAlarm має межу частоти, це треба знати. Перемикача в коді API
  немає.
* **Не вимикає старі релізи автоматично** понад `KEEP_EXTRA`: тримається
  чинний, ціль відкату й ще один (`CAMPTRIBE_KEEP_EXTRA`), тобто ≈26 ГБ.

## 8. Довідка

| файл | що |
| --- | --- |
| `infra/deploy-app.sh` | вхід з ноутбука; розв'язує SHA, дістає міграції з git, кладе виконавця |
| `infra/bin/camptribe-deploy` | виконавець на машині: `status`, `deploy`, `switch`, `rollback`, `rehearse` |
| `infra/deploy.selftest.sh` | перевірка самої процедури без сервера; біжить у CI |
| `/srv/camptribe/releases/<7 hex>/RELEASE.json` | повний SHA, ref, тема, час збірки, хто, `BUILD_ID`, перелік міграцій, хеші `dist` і `.env`, змінені відстежувані файли |
| `/srv/camptribe/deploy-history.jsonl` | рядок на перемикання: `at`, `action`, `from`, `to`, `sha`, `by`, `ok` |

Змінні виконавця (`CAMPTRIBE_*`): `ROOT`, `LINK`, `API_UNIT`, `WEB_UNIT`,
`API_PORT`, `WEB_PORT`, `BUILD_API_PORT`, `REPO`, `KEEP_EXTRA`, `MIN_FREE_GB`.
Їх змінюють лише тести й репетиція; перед перезапуском скрипт перевіряє, що
`WorkingDirectory` юніту лежить під `$ROOT/$LINK/`, і відмовляє, якщо ні.
